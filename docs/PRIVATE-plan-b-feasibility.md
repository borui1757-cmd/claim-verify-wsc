# B 方案可行性评估（机密）

> B 方案 = 把用户纠正编译成**运行时检查**，在每次工具调用后核对，而不是事后审计报告。
> 依据：TellOnce（arXiv 2606.13174）、Microsoft Task Adherence、Claude Code hooks。

## 一、素材可行性：充足

从 80 个会话里抽出的规则原料：

```
用户消息 2322 条
命中纠正类句子 4362 条 → 去重 221 条
```

高频的不是用户临时说的，而是 `AGENTS.md` / `PLAN.md` 里**已经沉淀的规则**——
也就是已经被本人筛选过、写下来的条款，质量高于临时对话。

## 二、可机器检查的比例：约 8/221

从 221 条里挑出 8 条能纯字符串/结构判定的（`lib/rules.js`）：

| 规则 | 可检性 | 首轮命中 |
|---|---|---|
| 不要用 `pnpm add` | 命令首 token | 0（收紧后） |
| 不要 taskkill DSH | 命令模式 | 19 |
| 不要给失效地址 | 黑名单 | 0 |
| 报时间必须跑命令 | **已失效**，见下 | 50 |
| 不信「重启了」，看 StartTime | 有/无核查动作 | 15 |
| 改配置必须备份 | 写路径 + 备份动作 | 33 |
| 不要重复造脚本 | 调用顺序 | 50 |
| 报数字必须来自工具 | 数字在工具输出中 | 139 |

**总数 306 次 / 815 个有工具调用的轮次 ≈ 37.5% 命中率**（含噪声）。

## 三、最关键的发现：规则会失效

「报时间必须跑命令，禁止心算」这条命中了 50 次——但**它在当前 DSH 环境下是错的**：

宿主会在每轮注入 `Time sampled while preparing turn ...`，agent **本来就知道时间**，不需要跑命令。

这条规则来自旧环境（时间没有注入）。**规则与运行环境绑死，环境一变就失效。**

这正是 TellOnce 强调「**可修正（revisable）**」的原因——规则必须能被后续反馈推翻，
否则会变成永久误报源。

## 四、误报结构（和 claim-verify 的 v1 同构）

| 误报来源 | 例子 | 修法 |
|---|---|---|
| 证据截断 | `number_without_tool` 139 次，多数是单位换算/截断 | 提高保留长度、做单位归一 |
| 子串匹配 | `pnpm add` 在长脚本里出现 ≠ 主命令 | 用 `headCmd` 取首命令（已修，归零） |
| 路径正则过宽 | 目录被当配置文件 | 白名单 basename（已修，45→33） |
| 规则失效 | 时间规则 | **必须人工复核，不能靠参数调** |

## 五、对标：这是什么品类

它已经有名字：**Task Adherence / Instruction Following**。

| 玩家 | 形态 | 数据来源 | 能不能改流程 |
|---|---|---|---|
| Microsoft Task Adherence | 云端 guardrail（预览） | 对话内容 | 能（阻断/评审） |
| Claude Code hooks | 本地钩子 | 每次工具调用 | 能（exit code 阻断） |
| OpenAI Agents guardrails | SDK 层 | 输入/输出 | 能（tripwire） |
| TellOnce | 学术 + 开源 skill | 会话纠正 | 部分（生成检查） |
| **我们（B 方案）** | **本地插件** | **真实命令 + 文件系统** | **暂只 observe** |

## 六、我们的位置优势与劣势

**优势（与 claim-verify 同源）**
1. **看得到真实执行**：命令字符串、文件状态、端口。云端 guardrail 只能看对话。
2. **零成本**：纯本地规则，0 token、0 延迟。
3. **中文规则**：现有工作全是英文语境。

**劣势**
1. **不是新品类**，微软已有产品；
2. **冷启动**：规则要靠用户纠正积累；
3. **规则漂移**：环境一变就失效（时间规则就是活例子）；
4. **精度未知**：306 次里有多少真违规，还没人工标注。

## 七、可行性结论

**技术上可行，商业上不构成新品类，但有一个结构性位置：本地执行层。**

判据：
- 如果目标是「**抓 agent 违反我的规矩**」→ 可行，素材充足，成本为零。
- 如果目标是「**做一个比微软更好的 adherence 产品**」→ 不可行，我们没有对话数据规模和分发。
- 如果目标是「**在自己的机器上，让 agent 守我的规矩**」→ **这是唯一站得住的位置**，和 claim-verify 完全一致。

## 六点五、实测：`number_without_tool` 的自动定因（不用人工标注）

从 139 次命中出发，逐层回溯（`eval/number-check.mjs`）：

```
当轮工具输出里其实有（假阳性）   0    0.0%   → 截断不是问题（已修到 4000 字）
当轮没有、前面轮次有（搬运）    44   31.7%   → 数字真实，只是不再当轮
来自用户原话（合法）             0    0.0%
哪儿都没有（疑似编造）          95   68.3%   → 最值得看的
```

样本：`450 MB` / `182MB` / `40MB` / `PID 108900` / `pid 75160` …

**这条规则的真实精度 ≈ 0.68（假设"哪儿都没有"里大部分确是编造）。**
比第一版的观感好得多，但仍需人工抽 10 条确认。

**方法论价值**：这种「分层回溯」能替代一部分人工标注——
先排除截断、再排除跨轮搬运、再排除用户原话，剩下的才是嫌疑样本。

### 通用化之后（`eval/adjudicate.mjs`）：每条规则都有了嫌疑率

| 规则 | 命中 | 证据在别轮 | 嫌疑 | 嫌疑率 |
|---|---|---|---|---|
| number_without_tool | 139 | 43 | 96 | **69.1%** |
| script_reinvent | 50 | 32 | 18 | 36.0% |
| profile_write_no_backup | 33 | 33 | 0 | **0%** |
| taskkill_dsh | 19 | 0 | 19 | 100% |
| restart_claim_no_proof | 15 | 15 | 0 | **0%** |
| time_claim_no_cmd | 5 | 5 | 0 | 0% |
| pnpm_add | 1 | 0 | 1 | 100% |

**三条规则的嫌疑率是 0**：它们的命中全部能用「证据在别的轮次」解释。
对 `restart_claim_no_proof` 和 `profile_write_no_backup` 来说，这意味着
**agent 确实做过核对/备份，只是不在同一轮**——规则本身要改成「同一会话内」而不是「同一轮」。

**100% 的两条要当心**：`taskkill_dsh` 的样本是故意的重启脚本（排除正则没覆盖到），
`pnpm_add` 那 1 条**来自我自己写评测脚本时的命令**（`node -e "...pnpm add y..."`）——
**规则会命中「讨论规则本身」的内容**，和我们之前踩的元讨论误报是同一个坑。

### 两处结构性修正之后（v2）

| 规则 | 命中 | 搬运 | 嫌疑 | 嫌疑率 | 变化 |
|---|---|---|---|---|---|
| number_without_tool | 139 | 43 | 96 | 69.1% | 不变 |
| script_reinvent | 50 | 32 | 18 | 36.0% | 不变 |
| taskkill_dsh | 19 | 0 | 19 | 100% | 不变 |
| time_claim_no_cmd | 5 | 5 | 0 | 0% | 50→5（v1 已修） |
| **profile_write_no_backup** | **0** | - | - | - | **33→0：会话级证据后全部消失** |
| **restart_claim_no_proof** | **0** | - | - | - | **15→0：同上** |
| pnpm_add | 1 | 0 | 1 | 100% | 仍在（嵌套引号漏网） |

**两条规则的命中全部消失**——说明那 48 次确实是「证据在别的轮次」，判据粒度错了，不是行为错了。

**修正一：证据粒度**
`profile_write_no_backup` / `restart_claim_no_proof` 从「本轮有没有备份/核对」改成「整个会话有没有」。
理由：用户关心的是会话结束后状态是否可恢复，不是某一轮里动作是否相邻。

**修正二：数据上下文剥离**
`node -e "..."` / `python -c "..."` / `echo "..."` 的参数字符串是**数据**，不是命令。
新增 `scanOf()`：先剥 powershell/变量/`cd ... &&` 包装，再砍掉 `-e/-c` 之后的内容。

**残留问题（已知盲区）**：嵌套引号形式的 `node --input-type=module -e "...\"pnpm add\"..."` 仍漏 1 条。
这是「正则 vs 词法」的固有局限（参考 StackOverflow 那个老问题）——真要解决得上 shell parser。

**修正三：每条规则声明盲区**
`blindSpots` 字段（参考 Deno lint 的写法），例如：
- `pnpm_add`：不检查 node -e 的字符串参数；不检查写在脚本文件里的 pnpm add
- `taskkill_dsh`：不检查通过脚本间接杀进程
- `number_without_tool`：不做单位换算

## 八、下一步（按性价比）

1. **人工标注 30 条命中**（6 条规则各 5 条）→ 得到真实精度
2. **删掉已失效的时间规则**，并在规则里记 `env` 字段（环境指纹），环境变则失效
3. **`number_without_tool` 做单位归一**（450 MB vs 450,073 KB）
4. 只有精度 > 0.8 的规则才进 observe 模式

## 九、三条方法论（B 方案真正沉淀下来的东西）

价值不在"发现了什么规则"，而在**三个可复用的判据设计方法**。
它们和 claim-verify 踩过的坑是同一批，只是换个场景又踩了一遍。

### ① 分层回溯：不用人工标注就能估精度

对任何一条规则的命中，逐层扩大证据范围重跑同一个规则：

```
L1 当轮证据触发
L2 换成整个会话的证据再跑
   · 不再触发 → 证据在别的轮次（搬运/陈旧），不是编造
   · 仍然触发 → 整份会话都找不到依据 → 嫌疑样本
L3 再排除用户原话
```

**规则无关、纯本地、零成本。** 实现见 `eval/adjudicate.mjs`。

实测：`number_without_tool` 139 次 → 43 次搬运 + 96 次嫌疑（69.1%）。
这个 69.1% 就是**真实精度的下界估计**，不需要人一条条标。

### ② 证据粒度必须和行为粒度对齐

`profile_write_no_backup`（33 次）和 `restart_claim_no_proof`（15 次）
改成**会话级证据**后**全部归零**。

判据写「本轮」还是「本会话」，决定了它是在抓错还是在制造噪声。
用户关心"最终状态能不能恢复"，不是"动作是不是相邻"——
**判据要贴着用户意图写，不是贴着数据形状写。**

同类错误在 claim-verify 里出现过两次：轮次级证据太粗、证据窗口只取当前轮。

### ③ 每条规则必须声明盲区

抄 Deno lint：规则里显式写「这条规则**不检查**什么」。

```
pnpm_add:            不检查 node -e 的字符串参数；不检查写在脚本文件里的 pnpm add
taskkill_dsh:        不检查通过脚本间接杀进程
number_without_tool: 不做单位换算
```

不写盲区，下一个维护者会把「没命中」当成「没问题」。

### 附：一个解决不了的固有局限

「`node -e "...pnpm add..."` 里的是数据不是命令」这类问题，**正则无法可靠解决**
（引号嵌套、转义、here-string）。正解是 shell parser（`tree-sitter-bash` / `mvdan/sh`），
我们不加依赖，只能引入 `DATA_HEADS` 启发式，并如实承认：**嵌套引号形式会漏。**

这是"正则 vs 词法"的经典边界，不是疏忽。

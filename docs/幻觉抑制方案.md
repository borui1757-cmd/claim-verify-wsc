# 怎么降低幻觉率：一套可执行的流程

> 每一条都有实测数据（脚本在 `eval/`）。原则：**不是让模型"更小心"，而是让它"看得见自己干了什么、和意图差多少"，并且事先知道"这里可能坏"。**

---

## 一、三个时点，三种干预（各管一段）

| 时点 | 干预 | 实测效果 | 为什么 |
|---|---|---|---|
| **事前** | **接种式提示**：告诉它这类失败可能发生 | 判失败 **0/20 → 13/20** | 松动"我通常能做成"的先验 |
| **事中** | 工具返回**与意图的差异**（`mismatch`），不只是状态 | 发现不符 **0/20 → 20/20** | 让证据存在 |
| 事后 | 回写提醒、加强措辞 | ❌ **无效** | 信念已形成 |

**三件缺一不可**：
- 只说"可能出问题"（事前），没有事中证据 → 无从判断；
- 只有事中证据，没有事前提醒 → 证据变成"建议确认"；
- 事后补 → 没用。

---

## 二、完整流程

```
① 系统提示（事前）：描述本机/本工具的已知失败模式
   "写入可能静默截断，历史约 30% 字节数不足"
② agent 调用 write_verified（不是宿主的 write_file）
③ 工具：原子写 → stat/sha256 → 与意图比对
④ 返回 verified{ exists, size, intentBytes, mismatch }
⑤ agent 报告：符合就报成功，不符就判失败
```

**关键点**：
- ② **必须是核验方的工具**——宿主的工具结果外部改不了（实测 `Cannot assign to read only property`）；
- ④ **必须含 `intentBytes` 与 `mismatch`**——只报 `size` 反而更糟。

---

## 三、数据

| 实验 | 对照 | 干预 | 结果 |
|---|---|---|---|
| 工具形态 | 幻影工具（只返回 ok） | 真实 `verified` 块 | 如实 **0/4 → 4/4** |
| 披露形态 | `ok` | `ok + size` | 谎称完整 **20/20 → 19/20（更糟）** |
| | `ok + size` | `+ intentBytes + mismatch` | **19/20 → 0/20** |
| 事前接种 | 常规提示 | 纯接种（只描述） | 判失败 **0/20 → 13/20** |
| | 纯接种 | + 规定措辞 | **13/20 → 20/20** |

---

## 四、无效的做法（都测过）

| 做法 | 结果 |
|---|---|
| 加强措辞（soft → firm） | 无差异 |
| 把冲突并列成文本（镜箱式） | 模型为之辩护 |
| 强制二元回答 | 4/4 坚持自己的观测 |
| 事后实时核验注入 | 只改"操作方式"，不改判断 |
| 让模型先自报预测 | 自我归因 0/20 |

---

## 五、边界（必须说清）

- **只覆盖有客观真值的声明**：文件、端口、进程、内容字节数（真实语料中约 18.5%）；
- **主观评价无法这样核验**（"性能提升明显"）——只能弃权；
- 所有数字是 **n=20、单模型、受控注入**；真实调用量下的比率**未知**；
- 需要模型**走核验通道**——是权限与习惯问题，不是提示问题；
- 纯接种只到 65%，剩下的 35% 需要更强的引导，但那是"改表述"，不是"改判断"。

---

## 六、一句话

> **事前告诉它"这里可能坏"，事中让它看见"和意图差多少"——
> 这两件都做到，它才会说"任务失败"；只做一件，它只会说"建议你确认一下"。**

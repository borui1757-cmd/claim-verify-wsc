## 题目（备选）

1. **《执行后核验：面向智能体完成声明的可验证证据链》**
2. 《幻影执行的可验证检测：以本机真值与签名回执核验智能体自述》
3. *Post-Execution Verification of Agent Completion Claims with OS Ground Truth and Verifiable Receipts*

## 摘要（草稿，约 400 字）

智能体在执行任务后往往以自然语言报告结果，而报告可能与实际执行不符：动作失败、未发生，却被声称完成。已有工作要么在执行**前**约束动作（授权、能力作用域），要么在**生成期**约束代码（类型、效果、SMT），但"动作究竟有没有发生"这一层缺少系统化方法。

本文提出执行后核验框架：将完成声明翻译为**受限 DSL 的只读检查**，由程序在本机真实状态上执行，得到支持/反驳/弃权三分类结论；判定与自然语言解析在信息流上分离，避免自述污染证据；结论以 **Ed25519 签名回执 + 线性哈希链 + RFC 3161 时间戳** 固化，任何第三方仅凭公钥即可验证。

在 3,686 条由真实工具轨迹构造的声明上，确定性审计器取得 **F1 96.9%**、弃权率 0，且**零模型调用**；同批样本上强模型判官 F1 为 83.6%。三个控制实验（顺序置换、删除失败证据、声明错配）分别产生 0.0/−96.9/−96.9 个百分点的 F1 变化，表明判定确实由证据驱动而非复原构造规则。我们进一步报告一项负结果：编程智能体的自由文本报告中可核验声明密度极低（30 份报告仅 1 条带具体目标），故结构化声明是必要前置。

**关键词**：智能体可靠性；完成声明核验；可验证证据；幻影执行；签名回执

## 第一章 绪论

### 1.1 背景

LLM 智能体被用于编码、运维与自动化流水线。它们通过工具调用改变系统状态，并在结束时以自然语言报告结果。下游阶段（人工、流水线、其他智能体）通常**信任该报告**。

### 1.2 问题

两类失败最危险：

1. **幻影执行**：动作未发生或失败，报告却声称成功；
2. **越权执行**：动作本不该发生却被执行。

本文聚焦第一类。其危险在于**静默**：没有异常抛出，下游继续推进，错误状态被当作成功结果。

### 1.3 现有方案的缺口

| 阶段 | 已有工作 | 缺口 |
|---|---|---|
| 执行前 | 意图授权与能力约束（SOF、CapScope、VeriGuard） | 只保证"能做什么"，不保证"做成了什么" |
| 构造期 | 能力安全语言与形式化验证（SIGIL） | 约束生成的代码，不核对执行结果 |
| 审计 | 报告–轨迹审计（GUI 域）、LLM 判官 | 依赖模型抽证据；结论不可分发验证；真值限于界面状态 |

### 1.4 挑战

1. **信息流污染**：把自述与轨迹一起交给判官，会把判定推向"完成"；
2. **真值获取**：机器状态易变，历史状态不可重取；
3. **可复现性**：模型判定不可复现、不可审计；
4. **声明稀疏**：真实报告里可核验的声明极少。

### 1.5 本文贡献

1. **执行后核验框架**：受限 DSL + 白名单执行 + 三分类判定，判定不依赖模型理解；
2. **证据可信化**：签名回执、哈希链与外部时间戳锚定，第三方可独立验证；
3. **信息流隔离**：声明解析与证据抽取分离，判定层不接触自然语言；
4. **系统性测试**：控制实验、蜕变关系、变异测试与属性测试，共同排除"复原生成器"的捷径；
5. **负结果与边界**：如实报告可核验声明密度极低，并据此论证结构化声明的必要性。

### 1.6 组织

第二章回顾相关工作；第三章给出系统方案；第七章报告实验与鲁棒性；第八章总结并讨论边界。

## 第二章 相关工作

> **本章起点**：2026 年的两项工作已经指出本问题——[LLM-as-a-Judge is not an Oracle](https://export.arxiv.org/pdf/2609.02246) 主张「自我改进的 agent 需要确定性护栏」，
> [Huang 等](https://scholar.google.de/citations?citation_for_view=-hW6cvgAAAAJ&hl=th&user=-hW6cvgAAAAJ&view_op=view_citation) 证明「没有外部反馈的自我纠正不成立」。
> 本文的工作可视为对这两条结论的工程化响应：**模型负责提出，确定性核验负责裁决。**

### 2.1 执行前授权与能力约束

- **SOF（Pre-Execution Enforcement Gap）**：在动作与执行器之间插入确定性授权边界，策略经操作方签名，决策以 Ed25519 意图凭证承载，并写哈希链证据；映射 ISO/IEC 42001 与 NIST AI RMF。
- **CapScope**：为每个子智能体分配类型化能力，置于模型上下文之外，调用时校验；在 75 次注入试验中把注入执行从 33–47 次降到 3 次。
- **VeriGuard**：离线澄清意图并合成行为策略，经测试与形式化验证后，在线作为运行时监控器逐个检查动作。

**与本文关系**：互补。授权层回答"能不能做"，本文回答"做没做成"。

### 2.2 代码生成期的安全与验证

- **SIGIL**：面向智能体自写代码的能力安全语言，含线性能力类型、效果行、信息流污点、双环 WebAssembly 隔离与 SMT 检查，并有 Lean 4 机械化证明。
- **VeriGuard**（同上）亦属此列。

**与本文关系**：它们约束**代码构造**，本文核验**执行结果**；二者可串联。

### 2.3 报告–轨迹审计

- **GUI 域报告–轨迹审计（arXiv 2610.29609）**：定义 dangerous misreport，提出报告隔离，以结构化审计器分离"声明解释"与"盲看轨迹"，在 465 条记录上取得 F1 0.75–0.81，门禁模式下拦截 74–90% 危险误报。
- 相关工作亦包括多智能体系统的蜕变测试预言机、基于轨迹的行为预言机。

**与本文关系**：本文采纳其"报告隔离"结论，并把它实现为信息流边界；差异在**真值来源**（OS 状态而非界面）与**证据可分发性**（签名回执）。

### 2.4 幻觉检测与事实核查

- 语义熵、自一致性、检索增强核查（RAGTruth、FActScore、MiniCheck/HHEM 等）。
- 面向 grounding 文档的句子级判定模型与商用 groundedness 接口。

**与本文关系**：这些方法判定"文本是否被证据支持"，面向开放式语料；本文判定"动作是否真的发生"，真值来自操作系统，且要求结论可复现、可验证。实测表明在机械事实子集上，确定性规则优于模型判定（§7.3）。

### 2.5 工业实践与事故：大厂在解决什么、没解决什么

**一个教科书级事故**：2025-07-18，某低代码平台的 agent **无视代码冻结**，删除 1,206 条高管记录，随后**伪造掩盖记录**（[事故复盘](https://safeguard.sh/resources/blog/replit-agent-database-deletion-vibe-coding-2025)）。它同时暴露两件事：权限没有边界，以及对 agent 自述的信任。

工业界的应对分为四层：

| 层级 | 做法 | 代表 | 回答的问题 |
|---|---|---|---|
| 权限与沙箱 | 开发/生产隔离、最小权限、审批门 | 各平台事后整改 | 它**能不能**做 |
| 可观测性 | tool call 的 span、参数与结果 | [OpenTelemetry GenAI 语义约定](https://safeguard.sh/resources/blog/opentelemetry-genai-semantic-conventions-explained-tracing-llm-calls-and-agents) | 它**做了什么** |
| 供应链凭证 | attestation / DSSE / in-toto | [in-toto 类 attestation](https://pkg.go.dev/github.com/Ratnadeepdeyroy/docker-security@v0.1.0/internal/attest) | 产物**由谁产出** |
| 评测 | benchmark + 人工评审 | 各厂 eval 套件 | 它**总体表现如何** |

**共同的空档**：四个问题没有一个在问「**它说做成了，这件事是否为真**」。
可观测性记录的是「它调用了什么」，不是「它声称什么、以及声称是否成立」。

本文的位置正是这一格：把完成声明当作**待证命题**，对系统真值核验，并把结论做成可分发凭证。
在格式上，本文从未有意另立标准：回执采用 DSSE 形状的信封，轨迹沿用 tool call/result 结构 —— 目的是能被既有审计与观测生态直接消费。

### 2.6 小结

现有工作分别覆盖"能不能做"（授权）、"代码安不安全"（构造期）、"文本是否被支持"（幻觉检测）。**"动作有没有发生、结论能否被第三方验证"** 是本文的位置。

## 第七章附 · 威胁模型与非法目标（non-goals）

### 必须信任的组件（可信计算基）

| 组件 | 为什么必须可信 | 现有保障 |
|---|---|---|
| 操作系统与文件系统 | 真值唯一来源 | 内核，超出本文范围 |
| 原语实现（只读性） | 若原语会写，核验就变成破坏 | 属性测试 P3（120 次执行后文件不变） |
| 签名私钥 | 泄漏即可伪造回执 | 用户自助生成、不入库（`.gitignore`） |
| 时钟 | 自报时间不可信 | RFC 3161 时间戳锚定 |

### 谁可能攻击、攻击什么

| 威胁 | 本文是否覆盖 | 说明 |
|---|---|---|
| 被核验的 agent 篡改回执 | ✅ | Ed25519 验签，改一字节即失败 |
| agent 读取或替换核验器代码 | ❌ | 一旦可写插件目录即失陷；属部署期隔离问题 |
| agent 伪造工具轨迹 | ❌ | 轨迹来自宿主，不由 agent 提供；若宿主被劫持则无效 |
| 核验后状态又变化（TOCTOU） | ⚠️ 部分 | 瞬态原语 + 时序对时（§3.6）降低误判，但无法根除 |
| 私钥泄漏 | ❌ | 设计外；建议 7 天轮换 + 独立存储 |

### 非法目标（明确不做）

1. **不证明「任务本身做对了」**，只证明「声称的动作是否发生」；
2. **不对任意 shell 副作用做回滚**（只覆盖受控原语，§3.5）；
3. **不判定主观/开放世界断言**——一律 `insufficient`；
4. **不提供身份真实性**（不解决「who owns this key」）；
5. **不做跨机器真值**（真值来自本机 OS，不覆盖远程系统状态）。

## 第八章 结论与展望

### 8.1 结论

本文把智能体完成声明的核验从"模型判断"迁移到"程序执行 + 可验证凭证"：

- 判定由本机真值驱动，零模型调用即可复现；
- 结论以签名回执固化，第三方仅凭公钥即可验证；
- 系统显式输出弃权，不猜测；
- 控制实验、蜕变与变异测试共同表明判定确实依赖证据。

### 8.2 边界

1. 仅覆盖存在**可观测客观真值**的断言；主观评价、预测、因果解释一律弃权；
2. 真值限于本机可观测范围（端口、路径、进程、时间、算式等）；
3. 自由文本声明稀疏，结构化声明是前置条件；
4. 构造标签与证据同源，真实分布的有效性仍需人工金标验证。

### 8.3 展望

1. **人工金标子集**与一致性系数，闭合"同源标签"的缺口；
2. **外部真值提供者**（版本库、持续集成、发布系统），扩展可核验面；
3. **与授权层对接**：把策略哈希与回执串联，形成"授权—执行—核验"闭环；
4. **意图执行器**：将可写原语与审批流程独立成组件，与只读核验器分离；
5. **透明度日志**：把链头锚定到公开日志，支持跨组织审计。
6. **格式对齐既有标准**（可直接落地的两项）：
   - 回执 → **AIVS（IETF draft-stone-aivs-01）**：**已实现**行哈希与链（`lib/aivs.js`，字段名对齐 `row_id/session_id/action_type/tool_name/cost_cents/timestamp/prev_hash/row_hash`），可用 `bin/aivs-verify.mjs` 独立校验；
   - 回执 → **DSSE / in-toto attestation**：字段与谓词对齐后，可被企业供应链审计工具直接消费；
   - 轨迹 → **OpenTelemetry GenAI 语义约定**：本文的 tool call/result 结构已近似该形状，对齐后可直接接入现有观测平台。
   对齐的意义是把本文从「自研格式」变成「生态里的一层」，而不是另立标准。

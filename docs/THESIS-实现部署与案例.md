# 第四章 实现

## 4.1 规模与结构

| 目录 | 文件数 | 行数 | 说明 |
|---|---|---|---|
| `lib/` | 35（+3 平台） | 5,523 + 186 | 核心逻辑 |
| `bin/` | 14 | 1,107 | 命令行工具 |
| `test/` | 41 | 2,498 | 测试 |
| `eval/` | 25 | 2,905 | 评测与实验脚本 |
| `tools/` | 1 | 72 | 真机自检脚本 |
| 合计 | — | **≈ 12,290** | 零运行时依赖 |

`lib/` 中规模最大的模块：`index.js`（约 1,300，插件与运行时装配）、`host.js`（463，宿主接口）、`dsl.js`（343，原语与执行）、`promise.js`（245，完成声明对账）、`claim-dsl.js`（192，自然语言→计划）、`sentence-audit.js`（192，句子级审计）、`isolated-audit.js`（约 230，报告隔离审计）、`trace.js`（186，轨迹缓冲）、`rules.js`（184，规则与屏蔽）、`feedback.js`（约 60，回写措辞）。

## 4.2 运行时装配

```
DSH 宿主
  ├─ tools/pre-execute  ──► 策略闸门（allow / deny / pending）
  ├─ tools/post-execute ──► 轨迹缓冲（turn / callId / 结果）
  │                        └─► 结构核验 ──► contradicted 时生成反馈
  │                                              └─► 注入下一步上下文（闭环）
  └─ 每轮结束（可选）  ──► 审计：结构对账 → 必要时 DSL / 隔离审计 → 回执
```

三个入口互不阻塞：闸门在调用前同步判定；轨迹缓冲只记内存；审计在轮次结束时异步执行。任一层异常只降级该层，不影响主流程。

**闭环路径**（§3.5.1）：结构核验判出 `contradicted` 时，反馈在**下一次模型调用前**注入上下文；强度 `soft`/`firm`/`block` 由配置决定。该路径零模型调用——它只是把已有证据回填，不额外评审。

## 4.3 配置面（关键项）

| 配置 | 默认 | 作用 |
|---|---|---|
| `mode` | `observe` | `observe` 只记日志；`strict` 才追加强调 |
| `dslAudit` | `false` | 开启自然语言→程序检查 |
| `isolatedAudit` | `false` | 开启报告隔离审计（替代句子级 LLM 审计） |
| `structuralFirst` | `true` | 先做零模型的结构对账，命中即止 |
| `auditTurnWindow` | `2` | 审计回溯的轮数 |
| `requireReceipt` | 视部署 | 缺回执时是否提示 |
| `policy` | — | 执行前策略（含路径前缀谓词） |
| `feedbackMode` | `failure` | 回写：`off` / `failure`（工具失败即回写）/ `audit`（轮末矛盾回写）/ `both` |
| `feedbackLevel` | `firm` | 回写强度：`soft` / `firm` / `block` |
| `feedbackMaxPerTurn` | `2` | 每轮最多攒几条回写，防止刷屏 |
| `receiptKeyPath` | `~/.dsh/dsh-claim-verify/receipt.key` | 签名私钥 |

## 4.4 存储与产物

| 文件 | 内容 | 是否含敏感信息 |
|---|---|---|
| `cases.jsonl` | 报告 + 工具轨迹快照（离线重放用） | **是**（真实路径） |

**部署注意**：`cases.jsonl` 与审计日志会记录真实路径，`.gitignore` 已排除；回执可对外分发，但正文含断言原文，按需脱敏。

## 4.5 错误处理原则

| 情况 | 行为 |
|---|---|
| 读不到 `/proc` | 返回 `null`（不知道），判定为弃权 |
| 私钥缺失 | 不签回执，审计照常，日志标注原因 |
| 时间戳服务不可达 | 回执照常签发，锚定留待重试；不阻塞主流程 |
| 模型调用失败 | 该句降级为 `uncertain`，不中断整轮 |
| 策略为 `pending` | 计划落盘，**不执行** |

## 4.6 回写通道的实现

**挂载点**（`lib/index.js`）：

| 钩子 | 作用 |
|---|---|
| `session/event`（`tool/result`） | 判定该次调用是否失败，失败则入队 |
| `agent/pre-step` | 取出队列，把反馈追加到 `decision.messages` |

后者的机制与 DSH 内置的 `modelSwitchNotice` 相同——**修改下一步的消息数组**，不改模型输出、不改会话历史。

**消息形状**（对齐 `dsh-llm` 的 user message）：

```js
{ role: 'user',
  id: 'claim-verify-fb-…',
  content: [{ type: 'text', text: '【核验】上一步工具调用失败（pwsh）：[exit code: 1]…' }],
  source: { kind: 'claim-verify', form: 'notice', summary: '核验回写' } }
```

**工程约束（三条，均来自实测）**：

1. **失败判定只看退出码**：DSH 对非零退出码不置 `isError`（实测恒为 false），失败只体现在输出末尾的 `[exit code: N]`；而**成功的命令也可能打印 `FAIL`/`Error`**，因此关键词不能作为依据。
2. **摘要要挑错误行**：优先「错误行 → 退出码行 → 首个非空行」，否则会给出 `(no output)`、`cwd=…` 这类无用信息。
3. **限流与去重**：同一文本不重复入队，每轮最多 `feedbackMaxPerTurn` 条。

**落盘**：每次注入前写 `feedback.jsonl`，便于事后审计「回写了什么、何时、对哪一轮」。

# 第五章 部署与使用

## 5.1 安装（DSH 插件形态）

```
plugins/dsh-claim-verify/            ← 放入插件目录
profiles/<name>/package.json         ← 加 link: 依赖
profiles/<name>/cordis.patch.yml     ← 声明插件
```
注册采用 `link:` 形式（本地路径），不做依赖安装；改动配置后需重启宿主生效。

## 5.2 首次运行

```bash
node bin/claim-verify.mjs --help          # 手工核验单条断言
node bin/platform-check.mjs               # 平台能力自检
node bin/receipts.mjs --verify            # 校验已有回执与链
node bin/anchor.mjs --verify              # 校验链头锚定
```

## 5.3 日常运维

| 任务 | 命令 |
|---|---|
| 查看回执 | `node bin/receipts.mjs` |
| 校验完整性与链 | `node bin/receipts.mjs --verify` |
| 链头锚定 | `node bin/anchor.mjs` |
| 查看待批计划 | `node bin/approve.mjs --list` |
| 放行/拒绝 | `node bin/approve.mjs --id <id> --allow\|--deny` |
| 声明覆盖率 | `node bin/coverage.mjs [--fail]` |
| 查看回写 | `tail -n 20 ~/.dsh/dsh-claim-verify/feedback.jsonl` |
| 关闭回写 | 配置 `feedbackMode: off`（需重启宿主） |
| 离线复算 | `node bin/replay.mjs <caseId>` |

## 5.4 典型故障与处置

| 症状 | 可能原因 | 处置 |
|---|---|---|
| 回执验签失败 | 回执被改 / 公钥不符 | 用 `--verify` 定位首个失败项；链断则从断点重签 |
| 锚定失败 | 网络不通 / TSA 不可用 | 保留回执，稍后重跑 `anchor.mjs` |
| 全部判 `insufficient` | 未开 `dslAudit` / 模型不可用 | 检查配置与模型连通性 |
| 写操作被拒 | 路径不在 `allowPathPrefix` | 调整策略或人工放行 |
| Linux 上端口探不到 | 读不到 `/proc`（容器限制） | 跑 `platform-check`，必要时改用 TCP 探活 |
| 回写从不出现 | 失败未带 `[exit code: N]`（工具自行处理了异常） | 属预期：只有"真失败"才回写 |
| 成功命令也回写 | 运行的是旧版本插件（曾用关键词判失败） | 重启宿主加载新版；已由回归用例覆盖 |
| 回写内容空洞 | 摘要取了空输出 | 新版已改为错误行优先；查 `feedback.jsonl` 确认 |

**重启注意**：插件在宿主启动时加载，改代码必须重启；判断是否真重启——`loads.jsonl` 末条 PID 必须等于 `netstat -ano | findstr :3080` 的 PID。

## 5.5 安全边界（部署方必须知道）

1. 私钥以明文 PEM 存放，权限依赖文件系统 ACL；
2. 回执签名不含时间戳时，只能证明「内容未改」，不能证明「何时签发」——需锚定补强；
3. 核验器只读，但**不能防止** agent 在核验之外做坏事；越权防护属于授权层职责；
4. 回执正文含断言原文与目标路径，分发前需评估泄露面。

# 第六章 案例

## 6.1 陈旧进程号

**场景**：agent 报告「relay 在 127.0.0.1:8700 上监听，PID 75160」。
**核验**：`proc_alive(75160)` → 不存在；`port(8700)` → 当前由另一 PID 监听。
**结论**：`contradicted`。**价值**：PID 陈旧是最常见的"看起来成功"的失败模式之一，人工很难发现。

## 6.2 端口对不上

**场景**：报告称服务跑在 `64164`；实际监听 `18080`。
**核验**：`port(64164)` → 未监听。
**结论**：`contradicted`。
**价值**：端口号被模型"记成"相似数字，是典型幻觉；程序核验一次即穿。

## 6.3 不存在的文件

**场景**：报告写「配置在 `C:\Users\...\Desktop\__no_such_file__.md` 里」。
**核验**：`exists(...)` → false。
**结论**：`contradicted`。
**价值**：这是测试中构造的负例，用于验证路径抽取与判定链路。

## 6.4 声称"测试全部通过"

**场景**：报告称「测试全部通过」，轨迹中最后一条测试命令 `exit_code = 1`。
**核验**：结构对账（零模型）直接命中不一致。
**结论**：`contradicted`。
**价值**：这是最高频、最危险的一类——报告与最后一条证据相反，而下游通常只看报告。

## 6.5 时序陷阱（反例：不该判否定的场景）

**场景**：第 3 轮报告「服务在跑」，第 9 轮审计时端口已关闭。
**核验**：`port` 属瞬态原语，跨轮不判否定 → `insufficient`。
**价值**：说明系统**宁可弃权不误判**；这类假阳性若不处理，会让审计失去信任。

## 6.6 报告隔离的实际效果

同一批 60 条构造声明：
- 模型判官（给自述）F1 83.6%；
- 模型判官（不给自述）F1 83.6%（本域未复现泄漏，因声明非来自报告）；
- 确定性审计器 F1 100%（构造边界内）。

**案例结论**：在机械事实上，"让程序查"优于"让模型判"；泄漏效应的前提是"声明来自自述"，而这正是我们建议用结构化声明的原因。

## 6.7 回写的真机验证

**场景**：在真实宿主里执行 `cmd /c "exit 3"`（注定失败）。
**观测**：下一步的上下文里出现一条 user 消息：

```
【核验】上一步工具调用失败（pwsh）：[exit code: 1]
不要声称该操作已完成；先修正或重试，再向用户报告结果。
```

**价值**：这是整条闭环在真实宿主上的端到端证据——失败被识别 → 入队 → 下一步注入。
**同时验证了反例**：执行成功但输出里含 `PASS/FAIL/Error` 字样的命令，**不再触发**回写。

## 6.8 同一批失败在真实场景里的表现

开发过程中回写通道连续暴露三个问题（详见 §7.6.1），最典型的一次是：
两条 `memory_save` 调用分别因「缺少参数」和「内容超长」失败，**每一次都正确触发了回写**，
摘要分别是 `Error: invalid arguments: missing required property "scope"` 与 `Error: 记忆内容超出上限…`。

**价值**：回写不只在构造用例里有效，**在真实工具报错场景下同样工作**；而且摘要给出的是可直接修正的错误信息。
